A VISUAL TOUR OF search-algorithms

Seven ways to find
a string.

Three questions (starts with, ends with, contains) asked of 100,000 real ISINs while the data keeps changing. See how each approach answers them, how much work it took to make two general-purpose engines fast, and why a few sorted arrays end up winning.

00

What we are testing

Every algorithm implements ISearchAlgorithm. An Entry(Key, Id) is what a query matches (Key) and what the caller gets back to find its entity (Id). The rules are the same for all seven:

  • Ordinal and case-sensitive. "us" does not start with "US". No culture rules, no normalization.
  • Result order is free. An index may return hits in whatever order is cheapest.
  • Everything is concurrent. Searches run while Add and Remove change the data, and a search that starts after a write returned must see it. Each implementation owns its synchronization.
  • Same answers. dotnet test checks every implementation against a plain LINQ scan, also after adds and removes.
THE DATA

Real ISINs

~9.4 million unique 12-character securities identifiers from GLEIF's ISIN→LEI mapping, such as US0378331005.

Medium = a seeded random sample of 100,000. Small (10k) is a subset of it, Huge (1M) a superset.

The Updates chart also runs on ~3.4 million legal entity names from GLEIF, such as Whisky & Genuss Dresden GmbH: 26 characters on average, up to 307, in many scripts.

THE QUERIES

3–6 character cuts

Prefixes, suffixes and middle fragments cut from random items with a fixed seed, so every algorithm answers exactly the same queries.

Short queries are the hard ones: they match many items.

01

Linear scan: check everything, every time

The baseline has no index at all. LinearScan keeps a HashSet<Entry> and, for each query, asks every item the question directly: Key.StartsWith(prefix), Key.EndsWith(suffix) or Key.Contains(fragment). It is short, obviously correct, and the reference the tests compare everyone else against.

private List<Entry> FindAll(Func<string, bool> match)
{
    _lock.EnterReadLock();
    try { return _items.Where(x => match(x.Key)).ToList(); }
    finally { _lock.ExitReadLock(); }
}
WATCH THE SCAN

Six items, six checks, whatever the question

LinearScan.FindAll

The cost is the number of items times the cost of one string check, for every query. At 100,000 ISINs that is 100,000 checks even when the answer is empty. Writes are cheap (one hash-set operation) but must take the lock exclusively, so a write waits for every running search to finish, and new searches wait behind the write.

02

Concurrent scan: drop the lock, keep the scan

ConcurrentLinearScan asks the same question of every item, but stores them in a ConcurrentDictionary<Entry, byte>. Enumerating it is lock-free, so searches never block and writers never wait for readers. The price is weaker consistency: a search running during writes may or may not see them.

ONE WRITE, TWO SEARCHES

Who waits for whom?

ReaderWriterLockSlim vs ConcurrentDictionary
Removing the lock did not make searches faster. The scan is still a scan, and walking a ConcurrentDictionary visits one heap-allocated node per item through its buckets, where a HashSet walks one dense array. In the measurements the concurrent version is the slower of the two for single queries. Locking was never the bottleneck; touching every item was.
03

Naive RocksDB: sorted keys, used for one question

RocksDB is an embedded key-value store that keeps keys sorted by their bytes. Writes land in an in-memory table and are later written out as sorted files; an iterator merges them into one ordered view. NaiveRocksDbIndex is the textbook setup: default options, one Put per entry, and one key per entry:

US990xFF00 00 00 05Key as UTF-8 · separator (never in UTF-8) · Id, 4 bytes · value: empty

Because the keys are sorted, StartsWith is easy: seek to the first key ≥ the prefix and read forward until a key stops matching. EndsWith and Filter get no help from that order, so the naive version reads every key and checks it in C#.

Every key read crosses from .NET into the native library, copies the key into a new byte[] and decodes a new string. A full scan pays that 100,000 times. The defaults cost more elsewhere too: a write-ahead log for an index that is rebuilt anyway, and a build that puts entries one at a time and never compacts.

04

Naive Lucene: a search engine, used literally

Lucene is an inverted index: a sorted dictionary of terms, each pointing to the list of documents that contain it (its postings). NaiveLuceneIndex indexes each entry as one document whose whole Key is a single term, and asks wildcard questions: US*, *9, *S9*.

A WildcardQuery becomes an automaton that is walked against the term dictionary. A pattern with a fixed start can skip straight to its region of terms. A pattern starting with * cannot: it must test every term. And each search here does more than walk terms:

FOLLOW ONE SEARCH

Filter("S9") → WildcardQuery("*S9*")

DirectoryReader.Open · Search · Doc

Each step is reasonable for full-text search, where you want the ten best-scoring documents. Here every hit is wanted, nothing needs a score, and the reader is reopened per query. So the textbook version pays for ranking, for loading stored documents, and for refreshing the index on every call.

The commit trail, with what each step measured
  1. Collect ids, reuse the searcher. Collector reads ids without scoring or stored fields; SearcherManager shares one searcher and reopens only after unseen writes.
  2. Decode each id into one string, not a CharsRef plus char[]: 128 → 48 B per hit.
  3. Return existing string instances instead of decoded copies.
  4. StartsWith / EndsWith as one term lookup via edge n-grams; reuse tokenizers per thread. StartsWith 2,745 → 1,570 μs, EndsWith 17 → 9 μs.
  5. Per-segment id table indexed by doc number: a hit costs an array index.
  6. Parallel build, one segment, edges up to 6 chars. Each extra segment cost every query a term lookup (EndsWith was 10× slower at 13–19 segments). 1M build 51.6 → 23.2 s.
  7. MMap behind NRT caching, no compound files. Buffered reads were 44–70% of every search. Under 1,000 writes/s: EndsWith 4,101 → 92 μs.
  8. Size result lists up front from the term's doc count: growing them was 56–63% of a large search.
  9. Per-thread flushes during build: Medium build ~3.1 → 2.6 s.

From the repository's commit messages; the numbers were measured at the time of each commit, on earlier versions of the benchmark.

What it still costs. The n-gram fields multiply the index: a 12-character ISIN is indexed as 57 n-grams (lengths 1 to 6) plus 6 prefix and 6 suffix edges. The build is the slowest of all seven, and every write makes the next search refresh the reader. Under a steady stream of writes that refresh is where Lucene's time goes.
06

What it took to make RocksDB fast

RocksDB can only do one thing quickly: walk a range of sorted keys. So the fix is to turn all three questions into starts with questions, by writing each entry several times in shapes where the answer is a prefix. A 259-line plan came first; it checked the binding's API, the key encoding and the edge cases before any code was written.

What it still costs. RocksDB has no "how many keys in this range" and no random access by position. A result's Count means stepping over every hit through the native binding, about 120 ns each. A one-character prefix that matches most of the data is a long walk, even when the caller reads only ten hits.

STARTS / ENDS WITH

Two binary searches win

The sorted array answers in under a microsecond and hands back a window onto its array without copying. The engines are fast only when few entries match: ISIN suffixes are selective, prefixes like US91 are not, and paying per hit makes RocksDB's StartsWith slower than a plain scan.

CONTAINS

The cost per hit decides

The sorted substring array and Lucene's n-grams beat the scans by more than an order of magnitude. RocksDB also reads only hits, but each one crosses into native code, so it lands close to the linear scan it was meant to replace.

THE BILL

Speed is paid for elsewhere

Lucene has the slowest build by far and allocates gigabytes doing it. The sorted array pays on writes: most only copy its small sorted delta, but every few thousand a merge rewrites all three arrays (about 130 MB at 1,000,000 ISINs). Counted in, as in "Updates", it beats RocksDB at 100,000 entries and is the slowest at 1,000,000. It also keeps everything on the heap, where Lucene and RocksDB keep files on disk.

BenchmarkDotNet short in-process job, 3 warmups and 5 iterations of 200 ms: good for orders of magnitude, not for small differences. Bars marked with a dash had no result.
