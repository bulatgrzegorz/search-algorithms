01

One collection, three ways to arrange it

We have these three unique strings: GB19, US12, US99. A plain scan would check each string for every request. This class does extra work up front so that each kind of search can jump to a smaller part of the data.

An index here is an arranged view of those strings. Think of three lists that answer three different questions:

STARTS WITH

"US" → US12, US99

Sort by reading from the left.

GB19US12US99

ByPrefix: the US strings sit together.

ENDS WITH

"9" → GB19, US99

Sort by reading from the right.

US12GB19US99

BySuffix: strings ending in 9 sit together.

CONTAINS

"9" → GB19, US99

Arrange the text starting at each position.

9 GB199 US9999 US99

Substrings: find the block, then remove repeated hits.

One rule makes all three work. In the right arrangement, all the matches are neighbors. We only need to find where that group starts and ends.

What does “sorted” mean for these strings?

Comparisons are ordinal and case-sensitive: compare the numeric UTF-16 values of the characters, without language-specific alphabet rules. "US12" comes before "US99" because, after the shared US, '1' is smaller than '9'. "us12" does not start with "US". There is no case folding or Unicode normalization.

Strings stand in for entries. The index really stores Entry(Key, Id): queries match the Key, and the caller gets the Id back to find its entity. Two entries may share a Key (two companies with one name); they then sort by Id. This page shows only the Keys, because every decision below is made on them.

The constructor first puts the input into a HashSet<Entry>. If we pass ["US99", "GB19", "US99", "US12"], the repeated US99 disappears. We index three unique strings.

02

Build the views, with actual text

Build creates two arrays of references to the original strings, plus an array describing starting positions inside them. The three construction tasks run concurrently through Parallel.Invoke.

The ending view reads right to left

For US12, read 2 → 1 → S → U. For GB19, read 9 → 1 → B → G. For US99, read 9 → 9 → S → U.

Now every string ending in "9" is in one block: [GB19, US99]. To search for "19", read the query from the right too: first 9, then 1. Only GB19 matches. The code compares backward; it does not allocate reversed strings.

The struct is called Substring, but it stores (Item, Offset, Repeat): not a copy of the text, and not even the string. Item is the string’s position in ByPrefix: GB19 is 0, US12 is 1, US99 is 2. US99 from position 2 is stored as (2, 2); the sorting code reads ByPrefix[2], which is US99, from position 2 and sees "99". A four-character string contributes four entries; our three strings contribute twelve. These are all starting positions, not every possible start/end pair. The page writes an entry as (US99, 2) where the string is easier to follow.

Why a number instead of the string? An entry is 8 bytes and holds no reference, so the garbage collector never has to look inside the array. When entries held the string (16 bytes), every merge at 1,000,000 ISINs produced a fresh array of 12 million references, and the next collection scanned all of them: a pause of about 26 ms after every merge. The price is one more array read whenever an entry is compared or returned.

Why count first, then sort the buckets?

Imagine putting entries into trays labeled by their first character. The '9' tray gets "9" from GB19, "99" from US99, and "9" from US99. A '1' tray gets "19" and "12". Entries beginning with 1 must come before entries beginning with 9, regardless of the remaining characters.

  1. Count. start[c + 1]++ counts how many entries begin with character c. For '9', the count is 3.
  2. Add the counts cumulatively. There are three entries before the '9' tray: "12", "19", "2". So start['9'] = 3, start['9' + 1] = 6. Its reserved slice is [3, 6).
  3. Fill. next starts as a copy of start. Each '9' entry occupies the next free position in that tray; incrementing next['9'] moves its cursor.
  4. Sort each tray. "9" precedes "99" because the shorter text runs out first. Equal text is ordered by the original Key, then Id: GB19 before US99. Trays with one entry need no sort.
  5. Fill Repeat. After sorting, calculate the duplicate information for each entry in parallel. Repeat does not affect sorting.
  6. Renumber. The three sorts run at once, so ByPrefix is not sorted yet while the entries are made: they first number strings by input order. Sorting ByPrefix also records where each string went, and one parallel pass rewrites every Item to its string’s ByPrefix position. The order of entries does not change, because ties compare the strings, not their numbers.

This is a counting-sort step followed by comparison sorts inside buckets. There are 65,536 possible UTF-16 code units; the start array has 65,537 slots so even the last bucket has an end position. Larger buckets are scheduled first, with NoBuffering, to avoid leaving a big sort until other workers are idle. The final arrangement is the same whichever worker finishes first.

Current constructor limitation: [] or only empty strings

The search rules can handle an empty view, and an empty string can be indexed alongside nonempty strings. However, constructing this version with [] or [""] throws: SortedSubstrings eventually calls Partitioner.Create(0, 0), which requires a nonempty range. At least one initial string must contain a UTF-16 code unit. This is an existing implementation limitation, not a requirement of binary search. Removing all strings after a successful construction can still produce an empty logical collection.

03

Find the two edges of "US"

In [GB19, US12, US99], the matching strings start at position 1 and stop just before position 3. We write this as [1, 3): include 1, exclude 3. The count is 3 − 1 = 2. Position 3 is a gap after the array, not another item.

0 · beforeGB19
1 · startUS12
2 · matchUS99
3end →

FindBlock returns ArraySegment(ByPrefix, 1, 2): a window onto those two array entries.

Binary search checks the middle of the remaining range. Because the strings are arranged, a comparison tells us which whole side cannot contain the edge. We discard that side and repeat. We do this twice: once for the start, once for the end.

When comparing against "US", GB19 is before the block, while both US12 and US99 count as matching. We compare just enough characters for the query. We are looking for the edges of a group, rather than stopping at the first match.

Why the unusual ~BinarySearch(...)?

The code supplies a pretend Boundary value. The start boundary sorts just before all matches; the end boundary sorts just after all matches. It always compares as +1 or −1, never 0, so BinarySearch always reports “not found.” The useful part is where that boundary would be inserted.

Start boundary belongs at 1→BinarySearch returns −2→~(−2) gives 1

The ~ operator is a bitwise complement. .NET encodes an unsuccessful search as ~insertionPosition; applying ~ again recovers the position. For the end, the code searches only the slice starting at start, then adds start back. Here the local end position is 2, so the absolute end is 1 + 2 = 3.

With "FR", the insertion position for both edges is 0: [0, 0), an empty result. With "ZZ", both are 3: [3, 3). With "", all strings match, even an empty string.

Compare for sorting versus compare for matching

PrefixOrder.Compare("US12", "US99") is negative: it must distinguish two items for sorting. PrefixOrder.CompareToQuery("US12", "US") and CompareToQuery("US99", "US") are both 0: they belong to the same query block.

Boundary.CompareTo reverses that item-versus-query relationship because .NET is asking how the boundary compares to the item. The start boundary goes left on a match; the end boundary goes right. IOrder<T> lets the same FindBlock machinery use the prefix, suffix, or substring comparison rule. These are struct comparers; the generic implementation allows specialized comparisons without a separate search implementation for every view. PrefixOrder and SuffixOrder carry nothing; SubstringOrder carries ByPrefix, because its entries hold item numbers and it must read the strings they name.

A short item behaves correctly too: "U" comes before a search for "US", because the item runs out before the query is fully matched.

For "AAAA", the entries starting at offsets 0, 1, 2, 3 have Repeat values 0, 3, 2, 1. With "AA", offsets 0, 1, and 2 match. Only offset 0 passes 2 > Repeat. The first occurrence represents the string, even when occurrences overlap.

What if US99 was removed or FR99 was just added?

  1. Find base hits. For "9", get GB19 at offset 3, US99 at offset 3, and US99 at offset 2.
  2. Locate the removed string’s representative. If US99 is in Removed, US99.IndexOf("9") gives 2, and a binary search of ByPrefix gives its number, also 2. Binary-search (2, 2) within the matching block: its block-relative position is 2. Save that in removedAt.
  3. Walk the block. Keep GB19, read from ByPrefix[0]. Skip the later occurrence of US99 using Repeat. Skip its first occurrence because its position is in removedAt. Sorting removedAt lets one cursor follow all removals.
  4. Check pending additions directly. FR99.Contains("9") is true, so append FR99 once. Added strings are never in Base, so they cannot repeat a base hit. Result: [GB19, FR99].

The small Added and Removed collections have prefix and suffix arrays, but no substring index. For contains searches, the code uses IndexOf on removals and Contains on additions. This keeps each write from copying a substring index for the pending changes.

The empty fragment is special. Every string contains "", including "" itself. An empty string has zero starting-position entries. Therefore Filter("") delegates to GetByStartsWith(""), which includes it.

06

Copy stretches. Insert US55. Skip US12.

Both query-time overlays and full merges use MergeSorted. It builds a plan of positions first. It does not sort the whole Base again.

Use Base [GB19, US12, US99], Removed [US12], and Added [US55]. Binary search locates US12 at position 1. US55 would be inserted at position 2, before US99. Those positions refer to the original input array, before any removal changes a position.

FOLLOW THE COPY

A new array from a plan of positions

MergeSorted · Merged.Copy

In Merged.Copy, from tracks the next unread position in the original array, to tracks the next free output position, and r / a track removal / addition events. Copy all unchanged entries before the next event in one span operation. Then either write the added item or advance past the removed one. Finish by copying the remaining tail.

When an insertion and removal share a position, insertion goes first. For example, Base [GB19, US12], Removed [GB19], Added [FR77]: FR77’s insertion gap and GB19’s removal are both at position 0. Write FR77, skip GB19, then copy US12. Result: [FR77, US12].

Knowing the count does not require copying the result

Merged<T> is a result that initially holds the plan. Its Count is just baseCount − removedCount + addedCount. For the "US" query above, that is 2 − 1 + 1 = 2. Reading Count does not build the combined result array.

Accessing an element or enumerating the result calls ToArray(), which copies the entire combined result and caches it. Asking for only the first item still triggers that copy. Concurrent readers may both create a copy; both contain the same values. Filter, in contrast, eagerly builds its list of hits.

When does the whole Base get replaced?

Publish merges when Added.Count + Removed.Count reaches max(256, _items.Count / 256), using integer division. The count is of pending items, not every write call. Add FR77 and immediately remove it: the pending count returns to zero.

At the threshold, Merge constructs new prefix, suffix, and substring arrays. For prefix and suffix it uses their already-sorted deltas. For substrings it generates every removed and added starting-position entry with SubstringsOf. It sorts the new entries; removed entries need no sort because their located positions are sorted instead. After copying, the new State has empty Added and Removed collections.

Substring entries are renumbered while they are copied

Substring entries name strings by their ByPrefix position, and the merge moves those positions. US55’s entries are made before US55 has a place, so they are numbered 3, one past the old ByPrefix: SubstringOrder reads numbers below 3 from the old ByPrefix and 3 onward from Added. Merged.NewIndexes turns the ByPrefix plan into a table from each old number to its new one:

Old ByPrefix [GB19, US12, US99] plus US55, minus US12 → new ByPrefix [GB19, US55, US99]
Old numberStringNew number
0GB190
1US12removed (−1)
2US992
3 · addedUS551

The substring copy passes every entry through that table: US99’s (2, 2) stays (2, 2), US55’s (3, 0) becomes (1, 0), and US12’s entries are skipped. That is one table read per entry instead of a plain block copy, done on all cores. It is what keeps the array free of references (see chapter 02).

Why wait? Replacing a large Base copies a lot of entries. Batching changes spreads that cost across writes. Larger collections get a larger threshold to reduce how often their large arrays are copied. The merge runs synchronously in the triggering writer while it holds the write lock; it is not a background task.

07

A reader can finish with the old view

Imagine Reader A searches for "US" just before a writer removes US12. Reader A may keep [US12, US99]. A later search must see [US99]. Changing the old array in place would make Reader A’s result unstable.

STEP THROUGH THE HANDOFF

One published State per search

Volatile.Read · Volatile.Write
  1. Reader A takes one reference. Volatile.Read(ref _state) gives it the old State. Its Base, Added, and Removed all come from that same State.
  2. The writer prepares a replacement. Under _writeLock, it changes _items and creates a State with US12 in Removed. The old State and arrays remain unchanged.
  3. Publish swaps the reference. Volatile.Write publishes the complete new State. No search sees a half-updated combination of arrays.
  4. Reader B starts after Remove returns. It sees the newly published State and filters out US12. Reader A can still finish against its old State.

Writers are serialized by the lock. Searches do not take that lock and can continue using the old State while a writer builds a merge. An earlier result can outlive a later merge because its arrays are still referenced; the garbage collector can reclaim them when nobody holds them.

The guarantee is one consistent State per individual search. Three successive calls are three reads and may see different writes between them. Existing results are snapshots, not live lists that update after every write.

What “unchanged arrays” means at the API boundary

The implementation never mutates published arrays and returns IReadOnlyList<string>. That is a read-only API contract, not a tamper-proof container: an unmodified Base window is an ArraySegment<string>, whose backing array can be recovered by a caller that deliberately downcasts. Treat returned results as read-only. The snapshot explanation assumes callers honor that contract.

Result order is not part of the interface contract. Prefix and suffix results follow their respective view order. Contains walks substring order, then appends matching additions in prefix order; its output is not guaranteed to be alphabetically sorted. If your caller needs a particular order, it must sort the result.

What work did we save, and what did we pay for?

With a million short strings, locating a prefix edge takes roughly twenty middle checks rather than inspecting a million items. We locate two edges. Comparing each entry still takes character work, and returning a million matching strings still means reading a million results.

The code is especially suited to short identifiers. The bucket construction still handles all UTF-16 code units, but long names or highly repetitive text change the memory and build-time tradeoffs. The original strings are reused, yet the starting-position structs, arrays, live set, deltas, result lists, and temporary copies all consume memory. See the measured benchmark results for context; the examples here illustrate behavior, not performance measurements.

A small glossary, using the same strings
Array
An ordered sequence of slots: [GB19, US12, US99].
Item number
A string’s position in ByPrefix: GB19 0, US12 1, US99 2. Substring entries store it instead of the string.
Offset
A starting position inside a string. In US99, offset 2 points to the first 9. These positions count UTF-16 code units; some visible Unicode characters occupy two.
Block / range
Neighboring array positions. [1, 3) includes positions 1 and 2.
Span
A view over existing contiguous memory, such as the characters "99" at the end of US99, without allocating that text as a new string.
ArraySegment
A window described by array, starting position, and count. The US block is a window starting at 1 with count 2.
Delta
The pending difference from Base: for example Added [FR77] and Removed [US12].
Snapshot
The three Base arrays built together. A State pairs one Snapshot with one Added delta and one Removed delta.
Materialize
Actually allocate and fill the planned result array, such as [US55, US99].
Common prefix
The shared beginning of two texts: "9" and "99" share one character.
